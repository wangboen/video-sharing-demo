# Video Comment System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a video comment system where comment creation is accepted by RocketMQ first, persisted asynchronously, read through PostgreSQL indexes plus MongoDB content documents, and hot comments are precomputed into Redis.

**Architecture:** The API accepts comment commands, generates Snowflake `commentId`, publishes a RocketMQ command, and returns `202 Accepted`. A consumer writes MongoDB comment content first and PostgreSQL relation/index rows second. Reads use PostgreSQL for visibility, sorting, ownership, and like counts, then batch-load MongoDB content and apply anonymization rules.

**Tech Stack:** Spring Boot 3.2.5, Java 17, Spring Data JPA, PostgreSQL, MongoDB, RocketMQ, Redis, Vue 3, Axios, Vitest.

## Global Constraints

- `commentId` is generated by Snowflake in the API layer before sending RocketMQ.
- RocketMQ receives the publish-comment command before comment content is inserted into persistent storage.
- MongoDB stores comment content and display snapshot fields, including historical `username`.
- MongoDB does not store `videoId` or `userId`.
- PostgreSQL stores comment relation, ownership, status, sorting fields, like count, and anonymization state.
- User rename does not rewrite historical comment usernames.
- User comment delete means anonymize the specified comment; the comment remains visible under the video.
- Hot comments are refreshed into Redis by backend scheduled jobs.
- Read API returns featured hot comments and normal comments separately.
- Featured comments require configurable `featuredLimit` and `featuredMinLikes`.
- Normal comments are sorted by time and paginated.
- Public comment responses must not expose `userId`.

```sql
CREATE TABLE comment_relations (
    comment_id BIGINT PRIMARY KEY,
    video_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'VISIBLE',
    like_count BIGINT NOT NULL DEFAULT 0,
    anonymized BOOLEAN NOT NULL DEFAULT FALSE,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    anonymized_at DATETIME(6) NULL,
    CONSTRAINT fk_comment_relations_video FOREIGN KEY (video_id) REFERENCES videos(id) ON DELETE CASCADE,
    CONSTRAINT fk_comment_relations_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    CONSTRAINT chk_comment_relations_status CHECK (status IN ('VISIBLE', 'HIDDEN', 'DELETED'))
);

CREATE INDEX idx_comment_relations_time
    ON comment_relations (video_id, status, created_at DESC, comment_id DESC);

CREATE INDEX idx_comment_relations_hot
    ON comment_relations (video_id, status, like_count DESC, created_at DESC, comment_id DESC);

CREATE INDEX idx_comment_relations_user
    ON comment_relations (user_id, anonymized, created_at DESC, comment_id DESC);

CREATE TABLE comment_likes (
    comment_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (comment_id, user_id),
    CONSTRAINT fk_comment_likes_comment FOREIGN KEY (comment_id) REFERENCES comment_relations(comment_id) ON DELETE CASCADE,
    CONSTRAINT fk_comment_likes_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE comment_command_status (
    request_id VARCHAR(64) PRIMARY KEY,
    comment_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    failure_reason VARCHAR(500) NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    CONSTRAINT uk_comment_command_status_comment UNIQUE (comment_id),
    CONSTRAINT chk_comment_command_status_status CHECK (status IN ('ACCEPTED', 'COMPLETED', 'FAILED'))
);
```
